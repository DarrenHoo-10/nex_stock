# 内部服务的 ZeroTier 路由规范

适用范围是部署环境里一个自有服务调用另一个自有服务。跨主机请求的每一跳都应使用 ZeroTier，包括鉴权、回调、后台任务和流式连接。同机进程用回环地址或 Unix socket。浏览器、飞书、交易所和外部模型厂商按各自入口访问；服务调用自有模型代理属于内部流量，代理调用外部厂商属于外部流量。

## 2026-11-11 切换前核查

| 调用方向 | 当时路由 | 核查依据 |
| --- | --- | --- |
| 首尔 Stock 入口 → Mac Stock | ZeroTier | 生效中的 Nginx upstream 和出接口 |
| Mac Stock → 首尔用户中心、NexBot 入口 | ZeroTier | 后端连接地址配置和 Mac 路由。NexBot 的下一跳见下行 |
| 首尔 NexBot 入口 → 东京 Core | 公网 | 生效中的 relay upstream。指定东京组网地址并使用原有 origin CA，可获得 Core 的鉴权响应 |
| 东京 Core → Stock | 首段公网，首尔到 Mac 为 ZeroTier | 服务进程的 Stock 根地址、域名解析和出接口；委托校验、历史同步和金融工具复用该地址 |
| 东京 Core → 用户中心 | 公网 | 身份提供方地址、域名解析和出接口 |
| Mac Stock、东京 Core → 自有模型入口 | 默认走 Mac 隧道或东京公网接口 | Stock 的模型渠道配置、Core 已启用的模型连接及主机路由。未发起模型推理 |

通过首尔组网入口、保留原 HTTPS 域名校验，Stock 健康接口返回 200，用户中心会话接口和两个模型入口的模型目录均返回 401（未携带凭据）。这验证了服务路由及 TLS；带身份的登录、推理和流式输出仍需在迁移验收时验证。本次范围为金融助手调用链和首尔相关入口。

## 网关与服务发现

1. 复用首尔 Nginx 作为首个组网入口。采用一份由部署维护的路由清单，每个内部服务登记域名、入口节点、后端组网地址或本机 socket、TLS 服务名、信任的 CA、健康路径和维护方。实际组网地址放在私有部署配置。
2. 从清单生成两类配置：服务进程的精确域名内网解析，以及网关的 upstream。前者决定调用方到网关的第一跳，后者决定网关到目标实例的下一跳。容器、工作进程和 macOS 的系统代理也要遵循同一份清单。迁移期支持由清单生成目前已有的连接 IP 设置。
3. 应用继续使用原 HTTPS 域名。按域名发送 Host 与 SNI，校验证书；各服务原有的用户身份、委托、CSRF 和访问范围继续生效。内网不可达时报告路由故障；需要容灾时配置第二个组网节点。任意用户输入的 URL 不进入受信任服务清单。
4. 网关记录服务名、实际 upstream、状态码、建连和上游响应耗时。发布检查从真实服务进程的网络环境确认连接对端、ZeroTier 出接口和 TLS；网关同时检查下一跳。公网 upstream 或业务进程经系统代理访问已登记服务应触发告警。

## 迁移与回滚

| 顺序 | 改动 | 验收 |
| --- | --- | --- |
| 1 | 东京 origin 只信任首尔指定的组网代理地址传递客户端 IP，然后切换首尔 relay 到东京组网地址 | 校验 origin 证书、日志中的客户端来源、普通 HTTPS、SSE 和 WebSocket |
| 2 | 东京 Core 的 Stock 和用户中心域名启用内网解析 | 查询、委托校验、登录和撤销；Mac 和东京两侧均查看实际对端 |
| 3 | Mac 与东京的自有模型渠道启用同一份路由清单 | 校验模型目录、一次合成对话、流式输出及目标服务身份 |
| 4 | 依次盘点其余内部服务、定时任务和容器 | 在统一清单登记业务方向；对已迁移服务关闭公网回退并监测路由漂移 |

每次只切一条调用方向，保留前一份部署配置，遇到异常显式回滚该项。比较同一个已授权操作的成功率和 p50/p95，覆盖冷连接和连接复用。组网验收和延迟验收分别记录。

## 生产部署与维护

首尔的私有清单 `/etc/nex-internal-gateway/routes.hosts` 使用 hosts 格式。一行登记网关的组网地址和各业务域名，两行分别登记东京和 Mac 的源站别名。仓库提供占位符示例，真实地址只存放在私有部署环境。首尔 dnsmasq 只在网关组网地址提供 TCP/UDP 53、读取这份清单，禁用外部递归。Nginx 到东京仍校验原域名及 origin CA；到 Stock 使用原有组网监听端口。

- **首尔**。将清单的源站别名同步进本地 hosts 的 Nex 管理块，发布 `internal-dns.conf.example` 为 `/etc/nex-internal-gateway/dnsmasq.conf`，替换监听地址，安装并启用 `nex-internal-dns.service`。更改清单后执行 `sudo systemctl kill -s HUP nex-internal-dns` 以重新读取清单；监听地址变化时重启 DNS。核对两个 origin 的 `getent ahostsv4` 结果后运行 `sudo nginx -t && sudo systemctl reload nginx`。日志中的 `peer=` 记录 NexBot 实际上游。
- **东京**。此节点已有 Tailscale DNS。业务域名从同一私有清单同步到系统 hosts 的独立 Nex 管理块（静态快照），保留其余解析配置。清单变化时同步更新该快照，用 Core 运行账号的 Node `dns.lookup(name, {all:true})` 及 HTTPS 健康或鉴权探针核对。正在使用的旧连接可能到关闭后才重新解析。
- **Mac**。为清单中的每个业务全名分别安装 `/etc/resolver/<服务域名>`，内容为 `nameserver <网关组网地址>` 和 `timeout 2`。用 `dscacheutil -q host -a name <服务域名>` 或 Stock Python 的 `socket.getaddrinfo` 检查系统实际选路；单独使用 `dig @<网关> ...` 只验证 DNS 服务。Mac 上已有的 Stock 聊天与用户中心专用连接设置可继续使用。
- **验收与回滚**。切换前保存 Nginx 配置、hosts 和现有 resolver 文件；先验证新地址的 TLS，经私网确认客户端来源再移除旧 relay 的来源信任。逐项恢复对应配置并重载，核对 Stock 健康、已登录聊天读请求和实际 upstream。恢复公网旧路线前应先恢复对应可信代理来源。不要删除无关的 hosts 或 resolver 配置。
